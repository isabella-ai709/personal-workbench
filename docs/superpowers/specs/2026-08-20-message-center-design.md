# 消息提醒中心设计规格

## 1. 目标

在 Personal Workbench 中新增一级版块“消息提醒”，作为整个工作台统一的消息中心。它集中承接两类信息：已经产生、需要用户知道的结果，以及带时间要求、需要用户作出决定的事项。

首版接入任务计划、商务合作和 AI 新闻资讯，并提供稳定的扩展接口，后续版块无需重新设计消息页面即可接入。首版只提供站内提醒，不接企业微信、个人微信、邮件或其他外部渠道。

## 2. 已确认决策

- 采用统一消息中心，不做分散在各业务页面里的独立通知列表。
- 普通消息只进入消息中心。
- 重要消息进入消息中心，同时在工作台导航的“消息提醒”入口显示红点和未读数量。
- 有截止时间且尚未处理的事项，在截止前 3 天生成重要提醒；临近截止仍未处理时升级提醒。
- 普通消息支持标记已读、稍后提醒、忽略和查看详情。
- 决策类消息支持推进、延期、更改和终止；有风险的操作需要确认。
- 首版接入任务计划、商务合作和 AI 新闻资讯，后续其他版块通过统一消息生产接口接入。
- 数据模型预留投递渠道字段，但首版渠道固定为站内，不实现外部推送。

## 3. 方案选择

### 3.1 简易通知列表，不采用

只保存标题、正文和已读状态，实现成本最低，但无法承接临期升级、稍后提醒和业务决策，后续会很快重做。

### 3.2 统一消息中心，采用

消息中心保存消息生命周期，各业务模块提供来源信息和可执行动作。它能同时覆盖“AI 新闻已抓取”这类结果通知和“合作即将到期”这类决策提醒，复杂度与当前需求匹配。

### 3.3 完整规则引擎，不采用

允许用户为任意对象配置条件、频率、渠道和动作，扩展性最强，但首版没有足够的真实使用数据来支撑规则编辑器和冲突处理。

## 4. 提醒分级与默认规则

消息分为三级：

- `normal`：普通信息，只进入消息中心，不触发导航红点。
- `important`：需要关注的事项，进入消息中心并触发导航红点与未读计数。
- `urgent`：已临近或超过截止时间且仍未处理的事项，在消息中心置顶并使用更强的视觉提示。

首版采用固定规则：

| 来源 | 触发条件 | 初始级别 | 升级条件 |
| --- | --- | --- | --- |
| AI 新闻资讯 | 一期新周报成功写入工作台 | `normal` | 不升级 |
| 任务计划 | 未完成、未删除且有 `dueAt`，进入截止前 3 个自然日 | `important` | 距截止不足 1 个自然日或已经逾期时为 `urgent` |
| 商务合作 | 未完成、未终止且有 `targetEndAt`，进入截止前 3 个自然日 | `important` | 距截止不足 1 个自然日或已经逾期时为 `urgent` |
| 商务跟进 | 状态为待处理且有 `dueAt`，进入截止前 3 个自然日 | `important` | 距截止不足 1 个自然日或已经逾期时为 `urgent` |

日期计算统一使用 `Asia/Shanghai` 的自然日边界。提前 3 天表示截止日期减去三个自然日，而不是固定的 72 小时。事项在工作台未运行期间进入提醒窗口时，下一次启动或打开消息中心仍应补生成提醒。

同一来源对象、同一提醒类型只能有一条活跃消息。重新扫描只更新级别、截止时间和正文，不生成重复消息。来源对象完成、终止、取消或删除后，对应未处理提醒自动关闭。

## 5. 消息生命周期

消息状态统一为：

- `unread`：尚未查看。
- `read`：已经查看，但不代表来源事项已处理。
- `snoozed`：暂时隐藏，在指定时间恢复为未读。
- `resolved`：对应事项已经处理，或用户完成了明确决策。
- `ignored`：用户明确忽略本次提醒，不改变来源事项。

打开消息详情只将该消息从未读改为已读。红点和数字只统计 `important`、`urgent` 且状态为 `unread` 的消息；普通未读消息不产生红点。

“稍后提醒”首版提供明天上午 09:00、3 天后上午 09:00 和自定义日期时间。恢复时重新检查来源对象：如果来源已完成或失效，直接关闭消息；如果仍有效，则按当时距离截止日期重新计算级别。

“忽略”只结束当前消息。对于同一来源和同一截止日期不再重复生成；如果用户之后修改了来源对象的截止日期，则允许按新日期生成新提醒。

## 6. 页面与交互

### 6.1 导航入口

在主导航中增加“消息提醒”，放在“首页”之后。入口显示铃铛图标；存在未读的重要或紧急消息时显示红点和数量，超过 99 条显示 `99+`。

路由为 `/notifications`。页面加载失败不影响其他版块使用。

### 6.2 页面结构

页面包含：

1. 标题区：显示“消息提醒”和当前重要未读数量。
2. 状态筛选：全部、未读、重要、稍后提醒、已处理。
3. 来源筛选：全部、任务计划、商务合作、AI 新闻资讯；来源列表由实际消息动态生成。
4. 消息列表：按紧急程度、提醒时间倒序排列。
5. 消息卡片：显示级别、来源、标题、摘要、触发原因、截止或发生时间及可用操作。

默认视图为“未读”。紧急消息排在重要和普通消息之前；同一级别内较新的提醒排在前面。空状态应说明当前没有需要关注的消息，不使用虚构示例数据。

### 6.3 普通消息操作

- `查看详情`：跳转到对应 AI 周报、任务计划或商务对象。
- `标记已读`：保留消息并移出未读视图。
- `稍后提醒`：选择恢复时间。
- `忽略`：二次确认后结束当前提醒。

### 6.4 决策类消息操作

- `推进`：任务计划从待处理或受阻变为进行中；商务合作弹出精简的状态选择器，只列出当前状态允许进入的后续阶段，不自动猜测；商务跟进使用“完成跟进”作为对应动作。
- `延期`：在消息卡片中选择新的截止时间并填写可选原因，保存后更新来源对象并关闭当前提醒。
- `更改`：跳转到来源对象编辑界面，不在消息中心复制完整业务表单。
- `终止`：任务计划新增 `cancelled` 状态并改为已取消；商务合作改为已终止；商务跟进改为已取消。执行前必须显示来源名称和影响，并要求确认。取消不是删除，记录仍可查看，也能与正常完成区分。

快捷操作必须调用来源模块现有的服务层用例，不允许消息模块直接修改业务表。操作成功后，来源数据与消息状态在同一服务端用例中完成一致性更新；失败时两边都保持原状。

## 7. 数据模型

新增 `notifications` 表：

```text
id                TEXT PRIMARY KEY
source_module     TEXT NOT NULL
source_type       TEXT NOT NULL
source_id         TEXT NOT NULL
event_type        TEXT NOT NULL
source_version    TEXT NOT NULL
title             TEXT NOT NULL
body              TEXT NOT NULL
severity          TEXT NOT NULL
status            TEXT NOT NULL
occurred_at       TEXT NOT NULL
due_at             TEXT
snoozed_until     TEXT
resolved_at       TEXT
ignored_at        TEXT
created_at         TEXT NOT NULL
updated_at         TEXT NOT NULL
delivery_channel  TEXT NOT NULL DEFAULT 'in_app'
metadata_json      TEXT NOT NULL DEFAULT '{}'
```

约束：

- `severity` 只允许 `normal`、`important`、`urgent`。
- `status` 只允许 `unread`、`read`、`snoozed`、`resolved`、`ignored`。
- `delivery_channel` 首版只允许 `in_app`。
- `(source_module, source_type, source_id, event_type, source_version)` 唯一，用于防止重复消息。
- `source_version` 对截止提醒使用截止时间字符串，对 AI 新闻使用 `reportId`。来源日期变更后可生成新版本提醒。
- `metadata_json` 只保存渲染和跳转所需的稳定快照，不作为业务事实的权威来源。

消息中心不复制任务计划、商务合作或周报正文。展示详情和执行动作时重新读取来源模块；来源不存在时显示“原事项已不存在”，并将消息关闭。

## 8. 生成与更新流程

### 8.1 截止提醒

新增 `NotificationScanner`，在服务启动完成后以及消息列表或导航摘要读取前执行轻量扫描：

1. 查询任务计划、商务合作和商务跟进中尚未结束且具有截止时间的对象。
2. 按统一时区计算与截止日的距离。
3. 对进入三天窗口的对象执行幂等 upsert。
4. 对已有活跃消息重新计算级别。
5. 关闭来源已经完成、终止、取消或删除的消息。
6. 恢复到期的稍后提醒，并重新验证来源状态。

扫描不使用常驻定时器，不要求工作台后台持续运行。首版数据量较小，可按模块批量读取；实现时仍需建立状态与截止时间索引，避免未来退化为无边界全表处理。

### 8.2 AI 新闻结果消息

AI 周报成功写入 `ai_news_reports` 后，在同一服务端写入流程中幂等创建普通消息。重复发布同一 `reportId` 只更新报告，不重复产生消息。

消息创建失败时，报告写入也应回滚，避免用户收不到已接入功能承诺的结果通知。外部 `ai-weekly` 仍可按现有幂等 PUT 重试。

### 8.3 扩展接口

后续业务模块只通过 `NotificationService.publish()` 提交标准化事件：来源、事件类型、来源版本、标题、正文、级别、发生时间、可选截止时间和跳转信息。业务模块不直接写消息表，也不自行计算导航红点。

未来增加外部渠道时，在消息生成后增加独立投递层。站内消息仍是事实源，外部投递成功或失败不能改变站内消息的业务状态。

## 9. 服务与接口边界

### 9.1 共享契约

新增消息、消息统计、筛选参数、状态转换、稍后提醒和快捷操作的 Zod 契约。来源模块和事件类型使用可扩展字符串常量，未知来源在页面上回退为“其他”。

### 9.2 服务端组件

- `NotificationRepository`：消息查询、幂等写入和状态更新。
- `NotificationService`：状态转换、统计、来源校验和发布事件。
- `NotificationScanner`：发现临期事项并升级或关闭提醒。
- 来源动作适配器：把推进、延期和终止转发给任务或商务服务。
- `notification-routes`：浏览器读取与明确写操作。

建议接口：

```text
GET    /api/notifications
GET    /api/notifications/summary
PATCH  /api/notifications/:id/status
POST   /api/notifications/:id/snooze
POST   /api/notifications/:id/actions/:action
```

所有写接口继续使用现有本地会话令牌和 Origin 保护。列表使用游标分页，首屏默认 30 条。

### 9.3 客户端组件

- `NotificationsPage`：筛选、分页、空状态和错误状态。
- `NotificationList`：排序后的消息集合。
- `NotificationCard`：内容、级别和动作入口。
- `NotificationBadge`：导航红点与数量。
- API 客户端：列表、摘要、状态更新、稍后提醒和快捷动作。

导航摘要使用独立轻量接口，并在消息状态变化后立即刷新。首版不做 WebSocket；页面重新聚焦或进入消息中心时重新拉取即可。

## 10. 一致性与异常处理

- 消息列表读取失败时显示重试入口，导航保留上一次成功统计，不把数量错误地归零。
- 状态操作使用乐观界面更新；服务端失败时回滚并显示原因。
- 快捷动作以服务端结果为准，禁止只更新消息而未更新来源对象。
- 同一消息的重复状态请求应幂等；已处理消息再次处理返回当前结果。
- 来源对象已被其他页面修改时，服务端重新校验并返回最新状态，客户端提示用户刷新。
- 扫描单个来源失败时记录可诊断错误，其他来源仍继续；失败来源不关闭现有提醒。
- 系统时间变化后以当前 `Asia/Shanghai` 自然日重新计算，不缓存跨日判断结果。

## 11. 测试与验收

### 11.1 单元测试

- 三天窗口、一日升级、当天和逾期的自然日计算。
- 已完成、终止、取消和删除对象不生成提醒。
- 同一来源版本重复扫描不产生重复消息。
- 截止日期变化后允许生成新版本，旧版本被关闭。
- 稍后提醒到期恢复时重新计算级别。
- 普通消息不计入红点，重要和紧急未读消息计入。
- 状态转换和重复请求保持幂等。

### 11.2 集成测试

- 新 AI 周报写入时原子创建一条普通消息，重复 PUT 不重复创建。
- 任务计划、商务合作和商务跟进进入提醒窗口后可被补扫描发现。
- 推进、延期和终止同时更新来源与消息，任一失败时事务回滚。
- 错误会话令牌、错误 Origin、无效动作和无效稍后时间被拒绝。
- 消息列表分页、筛选和排序稳定。

### 11.3 组件与端到端验收

1. 发布一份新 AI 周报，消息中心出现普通消息，导航不出现红点。
2. 创建三天后到期的任务计划，消息中心出现重要提醒，导航显示数量。
3. 把截止时间改为明天，提醒升级为紧急并置顶。
4. 对提醒执行延期，来源日期更新、当前提醒关闭，旧日期不再重复提醒。
5. 对提醒执行稍后提醒，到期前隐藏，到期后按最新级别恢复。
6. 完成或终止来源事项，对应提醒自动关闭。
7. 重启服务后消息状态、稍后时间和未读数量保持一致。
8. 窄屏下消息卡片、筛选和操作菜单不重叠、不裁切。

完成后运行 `pnpm check`、`pnpm test:integration` 和生产构建，并进行一次真实浏览器流程验收。

## 12. 首版不包含

- 企业微信、个人微信、公众号、小程序、邮件、短信或系统级桌面通知。
- 用户自定义提醒规则、频率、免打扰时段和复杂条件。
- WebSocket 实时推送、后台常驻调度和离线操作系统提醒。
- 多用户收件人、团队分派、评论和协作处理。
- 批量推进、批量终止或自动替用户作出业务决策。
- 消息全文搜索、长期归档统计和投递渠道分析。
