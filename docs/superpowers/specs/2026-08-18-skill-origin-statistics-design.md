# Skill 来源分类与顶部统计设计

## 1. 目标

修复 Skill 管理中“待确认”项无法清晰区分来源的问题，并在模块顶部增加可读的来源统计。用户能够看到系统辅助、插件、用户安装、自己生成和待确认 Skill 的分组；同时能够快速知道当前启用、可供 AI 使用的 Skill 数量。

## 2. 用户体验

Skill 管理页面标题区域下方显示四项统计：

- 可用于 AI：当前 `enabled` 为 `true` 的 Skill 数量。
- 系统辅助：来源为 `system` 的 Skill 数量。
- 用户安装：来源为 `installed` 的 Skill 数量。
- 自己生成：来源为 `generated` 的 Skill 数量。

统计卡片使用当前查询结果计算；缓存数据仍可显示，但页面继续显示现有的缓存只读提示。插件和待确认数量不放入四项统计，但会在列表分组和来源筛选中显示，避免把不同含义混在一起。

默认“全部来源”列表按以下顺序分组，并在组标题显示数量：系统、插件、已安装、自己生成、待确认。搜索和来源筛选先作用于数据，再渲染分组；空组不显示。单个 Skill 仍显示启用状态、说明和来源标签。

## 3. 来源判定

服务端继续使用单一、明确的优先级：

1. `system` 或 `admin` scope 判定为系统。
2. 位于 Codex 插件目录的 Skill 判定为插件，路径匹配大小写不敏感，并兼容 Windows 反斜杠规范化后的路径。
3. 对非系统、非插件 Skill，使用本地人工来源记录：`generated` 或 `installed`。
4. 其他 Skill 保持 `unconfirmed`。

系统和插件来源是受保护来源，不能被人工修改，也不能删除。待确认项可以被用户标记为“已安装”或“自己生成”；该标记保存到现有来源覆盖表中。插件和系统不会因为旧的人工覆盖记录而被错误降级。

## 4. 数据流与边界

App Server 返回 Skill 元数据；Skill 服务完成来源判定并返回 `SkillSummary[]`。客户端页面基于同一份摘要数据计算统计和分组，不新增数据库表，也不复制 Skill 正文。统计不单独请求接口，避免出现统计与列表数据不一致。

四项统计的定义是互相独立的：可用于 AI 是启用状态指标，另外三项是来源数量，因此一个已启用的系统 Skill 可以同时计入“可用于 AI”和“系统辅助”。插件、待确认仅参与分组和筛选。

## 5. 错误与降级

当 App Server 不可用时，沿用现有缓存降级行为；缓存列表可用于展示统计和分组，但所有变更操作保持停用。若来源无法识别，不猜测，显示为待确认，并保留人工确认入口。

## 6. 测试

- 单元测试覆盖系统/管理员 scope、插件路径的 Windows 变体、人工覆盖优先级和未知路径待确认。
- 客户端测试覆盖四项统计文字与数量、来源分组顺序、搜索/筛选后数量同步变化，以及空组隐藏。
- 回归现有删除保护：系统、插件、待确认不可删除；用户安装和自己生成的用户/仓库 Skill 保持原有规则。
